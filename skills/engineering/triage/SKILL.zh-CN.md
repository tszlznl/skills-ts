# Triage（分诊）

在项目的问题跟踪器（issue tracker）中，把问题（issues）沿着一个小型状态机（state machine）的分诊角色（triage roles）向前推进。

在分诊过程中，发布到问题跟踪器的每条评论或 issue **必须** 以这段免责声明开头：

```
> *此内容由 AI 在分诊过程中生成。（This was generated by AI during triage.）*
```

## 参考文档（Reference docs）

- [AGENT-BRIEF.zh-CN.md](AGENT-BRIEF.zh-CN.md) — 如何写出经得起时间考验的智能体简报（agent brief）
- [OUT-OF-SCOPE.zh-CN.md](OUT-OF-SCOPE.zh-CN.md) — `.out-of-scope/` 知识库如何工作

## 角色（Roles）

两类 **分类（category）** 角色：

- `bug` — 有东西坏了
- `enhancement` — 新功能或改进

五类 **状态（state）** 角色：

- `needs-triage` — 维护者需要评估
- `needs-info` — 等待报告者补充信息
- `ready-for-agent` — 规格完整，适合交给 AFK 智能体
- `ready-for-human` — 需要人类实现
- `wontfix` — 不会处理

每个被分诊过的 issue 必须同时携带且仅携带：一个分类角色和一个状态角色。如果状态角色冲突，先标记出来并询问维护者，再做其他任何事。

以上是规范角色名（canonical role names）——问题跟踪器里实际使用的 label 字符串可能不同。映射关系应当已经提供给你；如果没有，运行 `/setup-matt-pocock-skills`。

状态迁移（state transitions）：未打标的 issue 通常先进入 `needs-triage`；之后再迁移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。当报告者回复后，`needs-info` 会回到 `needs-triage`。维护者可以随时覆盖（override）——遇到看起来异常的迁移，先标记并询问，再继续。

## 调用方式（Invocation）

维护者用自然语言描述需求并调用 `/triage`。你需要理解请求并执行。示例：

- “给我看看有什么需要我关注”
- “我们看看 #42”
- “把 #42 移到 ready-for-agent”
- “哪些已经准备好让智能体捡起来做？”

## 展示需要关注的内容（Show what needs attention）

查询问题跟踪器，按时间从旧到新展示三个桶（buckets）：

1. **未打标（Unlabeled）** — 从未分诊过。
2. **`needs-triage`** — 正在评估。
3. **自上次分诊备注以来报告者有活动的 `needs-info`** — 需要重新评估。

展示数量（counts）以及每个 issue 的一句话摘要（one-line summary）。让维护者来选择下一步看哪个。

## 分诊一个具体 issue（Triage a specific issue）

1. **收集上下文（Gather context）。** 阅读完整 issue（正文、评论、标签、报告者、日期）。解析之前的分诊备注，避免重复询问已解决问题。使用项目的领域术语表（domain glossary）探索代码库，并尊重你要触及区域的 ADR（Architecture Decision Record）。阅读 `.out-of-scope/*.md` 并把任何类似的历史拒绝决策呈现出来。

2. **给出建议（Recommend）。** 告诉维护者你建议的分类与状态，并解释理由；同时给出与该 issue 相关的简短代码库概览（codebase summary）。等待指示。

3. **复现（仅 bug）（Reproduce）。** 在任何拷问（grilling）之前，先尝试复现：读取报告者步骤，追踪相关代码，运行测试或命令。汇报结果——成功复现并指出代码路径、复现失败、或信息不足（强烈的 `needs-info` 信号）。确认复现能让智能体简报（agent brief）更有力量。

4. **拷问（如需要）（Grill）。** 如果 issue 需要补全规格，进行一次 `/grill-with-docs` 会话。

5. **应用结果（Apply the outcome）：**
   - `ready-for-agent` — 发表评论形式的智能体简报（agent brief）（见 [AGENT-BRIEF.zh-CN.md](AGENT-BRIEF.zh-CN.md)）。
   - `ready-for-human` — 结构同智能体简报，但要说明为什么不能委托（需要判断、外部访问、设计决策、手工测试等）。
   - `needs-info` — 发布分诊备注（模板见下）。
   - `wontfix`（bug）— 礼貌解释，然后关闭。
   - `wontfix`（enhancement）— 写入 `.out-of-scope/`，在评论里链接该文件，然后关闭（见 [OUT-OF-SCOPE.zh-CN.md](OUT-OF-SCOPE.zh-CN.md)）。
   - `needs-triage` — 应用该角色。若已有部分进展，可选发评论说明。

## 快速覆盖状态（Quick state override）

如果维护者说“把 #42 移到 ready-for-agent”，就相信他们，直接应用角色。先确认你将要做什么（改标签、发评论、是否关闭），然后执行。跳过拷问。如果在没有拷问会话的情况下直接进入 `ready-for-agent`，询问维护者是否希望你写一份智能体简报。

## needs-info 模板（Needs-info template）

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

把拷问过程中已经明确的内容全部记录到 “established so far”，避免劳动丢失。问题必须具体且可执行，不能是“请提供更多信息”这种空话。

## 恢复上一轮分诊（Resuming a previous session）

如果 issue 上已有分诊备注，先读一遍，检查报告者是否回答了任何未决问题，并在继续之前给出更新后的情况摘要。不要重复询问已解决问题。
